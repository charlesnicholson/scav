Proof it holds

Determinism: goldens, hashes and selftest

The same chart, profile and fonts give the same drawing, byte for byte, on any machine, any compiler and any number of threads. scav proves this with three hashes per drawing, committed goldens, and a self-test that every build can run.

Three hashes

Every laid-out chart carries three 32-bit digests, all xxHash32 implemented in-tree. Lanes are assembled byte by byte, so big-endian machines agree.

  • Inputs digest: everything that is not geometry. That is the profile (all 52 fields), the router's name and version, the packer choice, and the space-request tables (the app's measured text sizes). A golden is reproducible only against a stated measurement policy, and this digest names it.
  • Structural hash: ranks, in-rank orders, port sides, and each route's bends as direction-turn tokens (not points). It is seeded with the model's own structural digest, so it says "this model, laid out this way". Rank and in-rank position are recovered from the rectangles (sorted distinct x per frame, then y within a column), never stored, so it can be recomputed from a finished drawing alone.
  • Coordinate hash: every rectangle, point and port coordinate.

The split localises a change. Translating the whole drawing moves only the coordinate hash. A remeasure that reorders nothing moves only the inputs digest and the coordinates. Seeding the geometry hashes with the inputs digest was rejected, because every remeasure would then read as a global reflow.

scav selftest and thread counts

The corpus and its goldens are compiled into the binary, gzipped. scav selftest lays every chart out at 1, 2, 3, 5, 8, 13 and 16 threads and diffs all three hashes against the embedded goldens (--against FILE substitutes a golden file). A difference from the golden is a toolchain finding. A difference from the 1-thread run is a sharding defect. One thread runs serially; every other count uses the one global pool, so the six pooled runs exercise different schedules of the same work. That is the point: a shard (a unit of parallel work) is fixed by the model, never by the thread count, and every reduction runs in index order, so the schedule cannot change the answer.

The determinism test class checks every geometry column's bytes, all three hashes and the Level 2 row that produced them. A worker count that moved the pick would move everything under it. It covers the 11 corpus charts and two 2,000-state synthetic charts at 2, 3, 5, 8, 13 and 16 workers against 1. It runs under a scheduling-delay injector: each shard yields rnd(seed, 0, shard, 0) % 64 times and spins rnd(seed, 1, shard, 0) % 4096 iterations. It also covers the inflation retry at 8 workers against 1, and a chart on which every row ties, so that index-ordered reduction is what decides. Timing never gates a determinism claim.

The CI matrix is six toolchain triples × {Debug, Release, testable} × the thread counts, about ten minutes per run. The testable build, which gives internal functions external linkage, must be byte-identical to Release. All layout arithmetic is integer, so inlining cannot change a result. A divergence means undefined behaviour.

Goldens

test_data/golden/layout/ holds corpus_hashes.txt (three hashes per chart), corpus_cost.txt and corpus_cost_measured.txt (every cost term per chart, at no text and at real text), corpus_cost_shares*.txt (basis points), and corpus_routers.txt (every registered router over the corpus), plus draw-list, dump and SVG goldens. The cost goldens and the gauntlet are measured at no text (no space requests). scav render, dump --layout and corpus_cost_measured.txt are at real text. The two scales are never compared directly.

How scav is tested

  • Unit means unit. No disk, no parsing, no earlier stage: inputs are typed in as plain structs. "A defect in rank assignment should fail one test that types in a graph, not a golden hash three stages downstream."
  • Functional tests compose the pipeline over the corpus.
  • The gauntlet: 28 element charts, one layout shape each, small enough to name every route, held to reader-visible properties rather than a hash. For example: no element routes an edge through a box; every route is axis-aligned, forward, and reaches its ends; a fork's bar is used along its length, not at one point; a transition and its return are two straight legs an em apart. A property that does not hold yet is carved out with a pinned count and the owning PRD section named: "a carve-out with no number on it is an excuse". The gauntlet scores what ships (the shipped profile's full search), not a candidate nobody draws.
  • Every rule gets an isolated test on a trivial layout, and every fixed bug leaves a test.
  • Every optimisation (each memo, reuse path and bound) has a test mode that re-runs the unoptimised computation and compares, plus a planted defect proving the test can fail.
  • Also golden, property (round trip, references resolve, zero box overlap, zero edge through a box), sanitizer (UBSan, ASan, TSan, MSan), fuzz (deserializer, resolver), binding (Python), baseline (side by side with PlantUML and elkjs) and regression tests. Performance tests assert floors, not times: throughput and memory ratios, never goldens.

The trace is a developer-facing list of events: rank assigned, edge reversed, node placed, net planned, candidate scored with its terms, fold cut, and so on. A trace forces one thread. layout_trace_json searches first, then lays the winning (row, pins) out again with the trace attached. All eleven corpus charts give the same hashes traced as untraced. The search path and round figures in the search section are read from this trace.

RejectedMocks and interface seams: tests get linkage to internals through an intrusive internal-section marker instead. A "stopped at cap" diagnostic for search loops: diagnostics are golden, so an improvement loop reports a counted statistic (sweeps, moves accepted, frames at cap) instead.
